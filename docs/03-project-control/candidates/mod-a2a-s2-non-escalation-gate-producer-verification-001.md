## What was built

1. **`src/control/delegation-gate.mjs`** — pure delegation non-escalation gate. Exports:
   - `evaluateDelegation({ requestedCeiling, boundingCeiling })` — pure, no I/O, deny-by-default. (a) calls the **existing, unmodified** `non-escalation-comparator.withinCeiling(requestedCeiling, boundingCeiling)`; any denial is returned **verbatim** (same object shape, same code, same `dimension`). (b) if the comparator allows, calls the **existing, unmodified** `risk-registry.riskProfile(requestedCeiling.riskClass)` and denies `DENY_HUMAN_APPROVAL_REQUIRED` if that risk class's `humanApproval` flag is `true` — mirroring `policy-decision-point.mjs`'s own documented invariant ("the PDP never substitutes for a human approval"): this gate doesn't substitute for one either, it only refuses to grant itself the authority to skip one. Otherwise returns `{ ok: true, code: "ALLOW" }`.
   - `evaluateDelegationRequest(delegationRequest, delegatorCeiling)` — a **zero-logic** convenience wrapper that extracts `.ceiling` from an S1-shaped delegation-request record and forwards it unmodified to `evaluateDelegation`. Added because the task instruction asked for a gate that "takes a delegation request (from S1's contract shape)," while the gap assessment's own S2 slice text explicitly scoped the *core* evaluator to operate "on ceilings directly, not on the delegation-request schema" (S1/S2 independence — see "Design decisions" below for how both were reconciled without contradiction).
   - `DENY_HUMAN_APPROVAL_REQUIRED`, `ALLOW` — the only two gate-owned code constants; every other code returned by this module (`DENY_ESCALATION`, `DENY_ESCALATION_UNCOMPARABLE`, `DENY_UNKNOWN_RISK_CLASS`) is a pass-through of a code an imported function already produces.
   - `buildDelegationDecisionRecord(evaluation, identity)` — pure candidate-minting function, same shape and discipline as `retry-policy.mjs`'s `buildRetryDecisionRecord`. Builds a `decision-record`-shaped object (`decision_type: "DISPOSITION"`, `outcome` = `"ALLOW"` or the exact deny code) but performs **no I/O** and holds no ledger authority. **No new ledger, no new schema, no new `decision_type` enum value** — reuses the existing `DecisionLedger` exactly as the task instructed and exactly as `retry-policy.mjs` established the pattern for MOD-RUNTIME.
2. **`tests/delegation-gate.test.mjs`** — 24 new tests (positive path, boundary, escalation matrix, uncomparable/fail-closed, human-approval invariant, S1-shape wrapper, verbatim-reuse parity, decision-record minting, real ledger recording — see "Tests" below).
3. **`MANIFEST.json`** updated +3 (the two new files above plus this record). ## Design decisions (advise-and-proceed, recorded per AMD-002 rule 3.1)

- **Reconciling the task's "S1-shape" instruction with the assessment's S1/S2 independence note.** The gap assessment's own §4 sequencing text is explicit: "S2 does not depend on S1 (it operates on ceilings directly, not on the delegation-request schema) and could be produced first if preferred." This slice's task instruction, independently, asked for a gate that "takes a delegation request (from S1's contract shape) and a delegator authority/risk profile." Both are honored without contradiction: `evaluateDelegation` (the actual decision function, importable and testable with zero dependency on S1's schema or `DelegationLedger`) is the assessment's literal API; `evaluateDelegationRequest` is a thin, zero-logic wrapper added on top that only reaches into `.ceiling` — it adds no comparison logic, does not import `DelegationLedger` or `contracts/delegation-request.schema.json`, and does not validate the request's shape itself (schema validation remains `DelegationLedger`'s/`validateContract`'s job, never duplicated here). An import-only grep (`grep -nE "^import|new DelegationLedger|validateContract\(.delegationRequest" src/control/delegation-gate.mjs`) returns only the module's own two functional imports (`withinCeiling`, `riskProfile`) — no `DelegationLedger` import, instantiation, or schema-validation call anywhere in the file, confirming the core module still has no S1 dependency. (An unfiltered grep for the bare token `DelegationLedger` does return 6 hits, all inside header-comment prose discussing the design rationale — not code; disclosed here for the same reason as the comparator/risk-registry grep above.)
- **Filename: `delegation-gate.mjs`, not `delegation-non-escalation-gate.mjs`.** The task prompt suggested the latter as an example ("e.g."); the gap assessment's own already-reviewed, literal S2 slice text (§4) names the file `src/control/delegation-gate.mjs` and the test `tests/delegation-gate.test.mjs`. Since the assessment is the more specific, already-reviewed bounded plan this task was dispatched to implement, its literal filename was followed for consistency with the rest of the MOD-A2A slice family (mirrors how S1 followed the assessment's literal field-mapping table rather than re-deriving its own).
- **A separate top-level `riskClass` parameter was deliberately NOT added**, despite the assessment's literal sketch `evaluateDelegation({ requestedCeiling, boundingCeiling, riskClass })` naming one. `requestedCeiling` already carries its own `riskClass` dimension (it is one of the five `non-escalation-comparator.mjs` dimensions S1's `ceiling` field imports verbatim). Accepting a second, independently-suppliable `riskClass` argument that a caller could pass out of sync with `requestedCeiling.riskClass` would introduce exactly the two-sources-of-truth drift risk the task instruction warned against (item 5) — just at the gate's own call-site boundary rather than inside its body. `evaluateDelegation` instead derives the risk class for the human-approval lookup from `requestedCeiling.riskClass` directly, the single field the comparator itself already validated as a recognized, ordered class by the time that lookup runs. This is a disclosed, non-regressive narrowing of the assessment's literal sketch, recorded here for asynchronous GOV ratification per AMD-002 rule 3.1 — in the same spirit as S1's disclosed field additions and MOD-RUNTIME S2's disclosed strict-typing strengthening.
- **Deterministic precedence: ceiling comparison before the human-approval gate.** `evaluateDelegation` checks `withinCeiling` first; only if that allows does it consult `riskProfile`. An escalating request (e.g. requested `R3` against a delegator bound of `R2`) therefore denies as `DENY_ESCALATION`, never reaching the human-approval question — tested explicitly (`evaluateDelegation checks ceiling escalation before the human-approval gate`). This matches the assessment's own literal ordering, "(a) ... to check the ceiling, and (b) ... to short-circuit."
- **`ALLOW` as the positive-outcome code, not a new doctrine literal.** No doc names a specific string for "this delegation was authorized" (unlike `retry-policy.mjs`'s doctrine-sourced `RETRY_AUTHORIZED` from `docs/templates/failure-evidence-envelope.yaml`). This module instead reuses the existing house convention already established by this exact module family's siblings — `DelegationLedger.resolveDelegationRequest` and `DecisionLedger.resolveEffective` both already return `{ ..., code: "ALLOW" }` on success. Reusing that convention, rather than inventing a new positive-outcome term, avoids adding a second vocabulary for the same concept.
- **`buildDelegationDecisionRecord` mints, never appends.** Mirrors `retry-policy.mjs`'s `buildRetryDecisionRecord` and `policy-decision-point.mjs`'s own documented discipline ("the PDP holds no ledger authority, the caller appends it"). Keeps the evaluator itself I/O-free and testable as a pure function, while the *test* demonstrates genuine, real, hash-chained ledger recording (task requirement 3/6) by calling `DecisionLedger.appendDecision` with the candidate this module produces — the same "candidate, not activation" pattern `retry-policy.mjs` already established, per the task's own explicit instruction to follow that precedent.

## Tests (24 new)

- **Positive path:** a requested ceiling strictly within the delegator's own bounding ceiling on every dimension allows.
- **Boundary (task-required):** a requested ceiling **exactly equal** to the bounding ceiling on every dimension allows (for a non-human-approval risk class).
- **Escalation matrix (task-required):** one denial case per ceiling dimension — `riskClass`, `dataClassification`, `paths`, `tools`, `transitions` — each confirmed to deny with `DENY_ESCALATION` and the exact `dimension` the comparator names.
- **Uncomparable / fail-closed:** glob in `tools`, `..` in `paths`, an unrecognized `riskClass`, and a fully malformed/missing ceiling (undefined, `{}`, null bound) — all denied via the comparator's own `DENY_ESCALATION_UNCOMPARABLE`/`dimension: "shape"`, confirming this module performs no separate shape validation of its own.
- **Human-approval invariant:** a within-bound `R3` and a within-bound `R4` request (both `humanApproval: true` in `risk-registry.mjs`) deny with `DENY_HUMAN_APPROVAL_REQUIRED` even though the ceiling comparison alone would allow; within-bound `R0`/`R1`/`R2` requests (all `humanApproval: false`) allow; an escalating `R3` request denies as `DENY_ESCALATION`, confirming the human-approval gate never even runs when the ceiling check has already failed (deterministic precedence).
- **S1-shape convenience wrapper:** `evaluateDelegationRequest` against the real `tests/fixtures/valid/delegation-request.json` fixture from S1 produces a result `deepEqual` to calling `evaluateDelegation` directly with the same extracted ceiling; a missing/malformed delegation request fails closed identically to a missing/malformed raw ceiling.
- **Verbatim-reuse parity (task-required "verify by reading your own gate's code"):** the 384-scenario matrix test described above under "Verbatim-reuse evidence."
- **Decision-record candidate construction:** `ALLOW` outcome on authorization; exact deny code as outcome on denial (including `DENY_HUMAN_APPROVAL_REQUIRED`); confirmed I/O-free (no ledger/filesystem touched to build a candidate).
- **Real ledger recording (task requirement 6 — not just returned):** an allowed disposition is appended via the real, unmodified `DecisionLedger.appendDecision`, then the ledger is **reopened from disk** and the persisted record's `outcome`/`decision_type` and the full hash-chain `verify()` are checked, plus `resolveEffective` resolves it `ALLOW`. All three denial-code dispositions (`DENY_ESCALATION`, `DENY_ESCALATION_UNCOMPARABLE`, `DENY_HUMAN_APPROVAL_REQUIRED`) are appended in sequence and confirmed persisted-in-order on reopen with a valid hash chain. A final adversarial test confirms this module does **not** duplicate or shadow `DecisionLedger`'s own contract validation: a candidate missing required identity fields is rejected by the ledger itself with `DENY_CONTRACT_INVALID`.
