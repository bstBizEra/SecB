## 0. Naming-ambiguity resolution (read before anything else below)

Two unrelated things in this workspace share the label "A2A":

1. **External Agent2Agent (A2A) protocol adoption** — a closed, evidence-only planning lineage in the separate `SecB-evidence` repository (`p0-a2a-adapter-plan-alignment-009`, and its predecessors `p0-a2a-adapter-planning-007`, `p0-a2a-official-source-intake-008`, `p0-09-a2a-readiness-006`). This concerns SecB acting as an **interoperability adapter** for the external, third-party A2A wire protocol (A2A v1.0.1, `POST /message:send`, `application/a2a+json`, signed Agent Card discovery at `/.well-known/agent-card.json`, JWS/JCS canonicalization, mTLS transport). Its own closure receipt (`09-alignment-closure-receipt.yaml`) records `terminal_state: PLAN_ALIGNMENT_APPROVED_CLOSED_R3_DENY_FAIL_CLOSED`, `implementation_authorized: false`, `repository_mutation_authorized: false`, `repository_or_Git_mutation: NONE`. Its planned write set (`src/a2a/agent-card-service.mjs`, `src/a2a/context-handoff-validator.mjs`, `src/a2a/a2a-gateway-service.mjs`, max 14 files) **does not exist anywhere in the SecB repository** — confirmed: `git ls-tree -r main --name-only | grep -i a2a` on SecB returns only `docs/07-capabilities/mcp-a2a-governance.md` and `src/services/non-escalation-comparator.mjs`; there is no `src/a2a/**` directory. This lineage never wrote a line of implementation code and remains gated on a separate, not-yet-authorized Human-GOV decision (`wp_secb_claude_code_candidate_selection_010`).
2. **The tracker's "MOD-A2A A2A Gateway" row** — SecB's own name, in `docs/10-platform/03-module-catalog.md` and `docs/14-delivery/01-module-allocation.md`, for the **internal** subsystem governing how SecB's own agents/roles hand off and delegate work to one another *within* the platform's project/work-package/session boundary. Its catalog description is literally "Delegation, handoff and non-escalation" — three named sub-concerns. `docs/07-capabilities/mcp-a2a-governance.md` ("SECB-FEDERATION-001", DRAFT/NOT EFFECTIVE) has a dedicated "A2A Gateway" section describing this same internal concept: "Every delegation declares source, destination, objective, scope, inputs, expected output, acceptance criteria, authority ceiling, tools, skills, data, budget, due condition, evidence obligations, and escalation route" — a doctrine statement about SecB's own delegation model, not about the external protocol's wire format.

**Conclusion: these are different concepts that happen to share an abbreviation.** The tracker row is unambiguously about (2), the internal delegation/handoff/non-escalation subsystem — confirmed directly by its own text ("handoff service P0-11 delivered... non-escalation gateway missing": P0-11 is `src/services/handoff-service.mjs`, an internal SecB service, not anything in the external-protocol lineage) and by the P0-11 planning packet's own explicit scope boundary: *"No transport, wire protocol, agent discovery, or live A2A runtime — transport belongs to P0-15/P0-16 adapters"* (`docs/03-project-control/candidates/p0-11-planning-001.cortex-advisory.yaml`, `explicit_non_scope`). This assessment proceeds entirely on concept (2). Overlap with concept (1) is addressed explicitly in §5 (non-goals) and the dedicated overlap note in §8; it is genuinely minimal and does not change the scope below.

## 3. Boundary notes

- **B1 — Handoff vs. Delegation.** P0-11's `HandoffService` deliberately models the review/report transfer — a work package's *review responsibility* moving from one role to another **within the same work package, post-execution** — not the forward act of *assigning new work* with a budget, due condition, and required skills to an agent **pre-execution**. The catalog names these as (at least) two sub-concerns ("Delegation, handoff and non-escalation"); only "handoff" (plus "non-escalation," used inside it) is delivered. A MOD-A2A slice plan should build "delegation" as a **sibling** surface that reuses the same non-escalation-comparator and grant/SoD machinery, not fold it into `HandoffService`, whose ledger/state-machine (`OFFER → ACCEPTED/DECLINED/REVOKED`) is shaped for a two-party, same-work-package exchange, not an open-ended task-assignment lifecycle.
- **B2 — Internal A2A Gateway vs. external A2A protocol adapter.** Per §0, these are unrelated workstreams sharing an abbreviation and, more substantively, a **design principle** ("a delegate/receiver cannot receive more authority than the delegator/sender possesses") — the external lineage calls this a decision through `AdapterAuthorityPolicyPort`; this module calls it the non-escalation comparator. If the external-protocol implementation is ever authorized, its gateway service would be a natural *future consumer* of this module's non-escalation primitive (both need the same "is this delegated authority within bounds" check). That is a well-scoped future integration point, not a present overlap requiring resolution — see §8.
- **B3 — Escalation route vs. GOV revocation authority.** `HandoffService` already lets "the source actor or GOV" revoke an `OFFERED` handoff — a *containment* path, not an *escalation* path. Any new escalation-route primitive (MA-2) should compose through the same actor model (GOV as the fixed escalation target) and the existing `DecisionLedger`, not invent a parallel notification/escalation channel with its own actor vocabulary.
- **B4 — Destination role vs. destination agent instance.** Per MA-5, a general delegation surface that must address a *specific agent instance* (not "whoever holds role X on this work package") needs to bridge `HandoffService`'s role-based destination model and `RuntimeRegistry`'s `agent_instance_id`-based identity model. This assessment does not propose building that bridge in S1–S3 below (see non-goals); it is named so a future slice does not silently assume one model subsumes the other.
