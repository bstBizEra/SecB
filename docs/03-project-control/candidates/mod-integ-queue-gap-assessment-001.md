## 3. Boundary notes

- **B1 — `DurableLedger` / `preWriteCheck` reuse (MI-6/MI-7).** An `IntegrationQueueLedger` must be a thin `DurableLedger extends` subclass, following the `EventLedger`/`CheckpointLedger`/`DelegationLedger`/`WorkspaceLeaseLedger` pattern exactly, and its "is this branch/slot already claimed" business check must be a `preWriteCheck(records, entry)` hook evaluated inside `append()`'s existing lock — never a separate unlocked `read()` taken before a locked write. This is not a stylistic preference: it is the exact fix this project has already had to apply after the fact to `WorkspaceLeaseLedger` and to `assessEnvelopeConformance` (MOD-LIVE), and the exact fix the MOD-SKILL addendum recommends designing in from the start for its own promotion/revocation gates. An Integration Queue slice built any other way (e.g., a bare in-process `Map` plus an audit-sink ledger, the same shape `capability-registry-service.promote()` and `SkillCandidateRegistry` currently use) would be the *fourth* instance of this exact bug class, this time in the one module whose entire purpose is preventing collisions between concurrent producers.
- **B2 — Integration Queue vs. Workspace Lease (MOD-WSPACE).** A workspace lease (item 10) answers "may this actor mutate this write set right now" — a workspace-scoped, time-boxed authorization. An integration-queue entry answers a different question: "where does this already-produced candidate sit in the order of things waiting to merge to a protected branch, and does it collide with another candidate also waiting." A lease is about *permission to work*; a queue entry is about *sequencing already-done work toward a protected-branch merge*. They are adjacent and a live system would likely consult both (a candidate's declared write set, checked at lease-grant time and again at queue-collision time), but this assessment does not propose folding one into the other — `WorkspaceLeaseLedger` is not the right base to extend for queue entries; `DurableLedger` directly is (B1).
- **B3 — Integration Queue vs. MOD-WORK's goal graph.** No overlap. `GoalGraphService` (item 11) sequences *portfolio work* (why a work package exists, what objective it advances); an integration queue sequences *candidate branches waiting to merge*. A work package can exist and be fully done with its traceability index populated regardless of whether its implementing branch has merged yet — these are two independent axes, not the same concern named twice.
- **B4 — Collision detection is MOD-WSPACE's `overlap-policy.mjs`, reused, not re-derived (MI-3).** ADR-0007 and the tracker's own "one producer per FILE SET" rule (item 12) describe exactly the O-ladder `overlap-policy.mjs` already codifies, including the doctrine's own O5 "Protected branch… → Serialized and human authorized" class, which is the literal ADR-0007 rule for `main`. An Integration Queue slice's collision check between two pending candidates' write sets should call `evaluateOverlap`, imported read-only, exactly as `delegation-gate.mjs` (MOD-A2A S2) reuses `non-escalation-comparator.withinCeiling` and `risk-registry.riskProfile` rather than re-implementing ceiling logic a third time. Building a second, queue-local overlap classifier would repeat the MOD-GOV "K-9 non-converging parallel implementations" mistake this project has already named and corrected for elsewhere.
- **B5 — Row 1's reconciliation record is not this module's S1.** Row 1's one-time reconciliation (§0) produced a *record*, not a *service* — it cannot be "extended" into a queue module because it has no persistent data structure, only a point-in-time Markdown report. It remains useful only as an existence proof that "serialized merge, done by hand, once" is achievable and auditable; the slice plan below does not depend on or modify it.
- **B6 — the tracker table itself is not replaced by this plan.** The dispatching instructions for this assessment explicitly forbid touching the queue table (already corrected by a separate agent) beyond one append-only log line, and this assessment agrees with that boundary independently: the tracker markdown file remains the operator-facing coordination surface for the remainder of this module loop regardless of what MI-1's slice below produces. S1 below is a **candidate**, parallel data structure — it does not read from, write to, or supersede the tracker file, and nothing in this plan proposes migrating tracker state into it in this round.

## 6. TOCTOU / check-then-act risk (explicit flag, dispatch requirement)

This is the single most important design constraint for this module, because MOD-INTEG's entire purpose is preventing exactly the class of bug the project has already shipped three separate fixes/flags for this session:

1. **MOD-LIVE** (`bst/mod-live-s1-toctou-fix-001`, N1): `assessEnvelopeConformance` took field values via live getters at different points instead of one atomic snapshot, letting a sibling-field getter fabricate or suppress findings. Fixed by snapshotting all fields via `Object.getOwnPropertyDescriptor` **before** any getter runs.
2. **MOD-WSPACE** (`bst/mod-wspace-s3-single-writer-toctou-fix-001`, commit `108bd0f` + fast-follow `338ba04`): `WorkspaceLeaseLedger`'s single-writer gate took an unlocked `read()` snapshot before the locked `append()`, so two producers could both pass a stale "no active lease" check and both write — fixed by moving the check inside `append()`'s lock via `preWriteCheck`, then further hardened when a second review found `preWriteCheck`'s `entry` argument itself was not being cloned (a second, independent instance of the same non-atomicity discipline, one level deeper).
3. **MOD-SKILL** (addendum `bst/mod-skill-s2-design-addendum-001`, not yet built): flagged, *before any code was written*, that a promotion/revocation gate built the same way `capability-registry-service.promote()` currently works (an in-process `Map` plus an audit-sink ledger) would inherit the identical check-then-act gap the moment more than one instance shares the underlying store — and recommended designing the state store as a `DurableLedger` subclass with the business check inside `preWriteCheck` from the start, rather than requiring a second-review fix round the way MOD-WSPACE needed.

An Integration Queue module is, structurally, a **"is this the next item in queue" / "is this branch already claimed" checker** — precisely the shape of question this bug class attacks. Any implementation of MI-1/MI-2 (or the sketched MI-3/MI-4 slices) that (a) reads current queue state via an unlocked `read()` and (b) later writes based on that stale read, is not merely a style deviation but a **reproduction of a bug this project has already paid to fix twice and flag once**. Slice S1 above therefore designs the duplicate-claim check into `preWriteCheck` from its first line of code — citing `DurableLedger`'s own `preWriteCheck` hook (`src/ledger/durable-ledger.mjs` lines 113–136, and the `WorkspaceLeaseLedger` consumer at item 8 above) as the established, twice-battle-tested solution shape, not a novel proposal.
