## 3. Boundary notes

- **B1 — Checkpoint vs. Context Receipt.** `docs/templates/context-receipt.yaml`/`ContextFederationService` (MOD-CONTEXT) already owns "what context was in scope at a point in time." A MOD-RUNTIME checkpoint is a different thing — "what execution/session state can this session be resumed from" — and must not be folded into or confused with a context receipt. The stale test-skip reason in item #17 ("P0-10 Checkpoint federation") suggests this exact confusion has already leaked into one comment; MR-1's slice should use unambiguous naming (`checkpoint`, not "context checkpoint") to avoid repeating it.
- **B2 — Retry vs. Failure Evidence Envelope.** `04-failure-to-capability-loop.md` places retry authorization *after* a Failure Evidence Envelope and a corrective decision — retry is not a bare loop-and-hope. MOD-RUNTIME's retry primitive should consume a caller-supplied "corrective decision was made" signal (e.g., a `DecisionLedger` DISPOSITION entry) rather than independently deciding a retry is warranted; MOD-EVID/MOD-GOV own the failure/decision substrate, MOD-RUNTIME owns the budget/backoff mechanics.
- **B3 — Approval vs. Authority grant.** V-009's existing passing implementation (item #20) shows the WP lifecycle already gates GOV-role transitions through the ordinary `AuthorityEngine` grant path — that is authority, not a distinct "approval record." A MOD-RUNTIME approval gate for retries/checkpoint-restores should bind through the **same** grant/decision-record machinery (extended, per MR-3) rather than adding a fourth approval shape alongside items #9/#10/#20.
- **B4 — Checkpoint state vs. Session state machine.** Widening `STATE_MACHINES.Session` (MR-4) is a live, authority-adjacent kernel file (`state-machine.mjs` is consumed by `TransitionEngine`, which every hardened service's `#serviceAuthorize`-style mirror ultimately traces back to per MOD-GOV's K-9 note). This assessment does **not** propose editing it — see non-goals.
