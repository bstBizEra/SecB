## Verdict

**REQUEST_CHANGES**

Within a single, continuously-running process, the S2 ladder and S3 resolver are genuinely sound: SoD is correctly enforced (verifier ≠ producer; acceptor ∉ {producer, verifier}), every edge is source-and-target gated read-only against the canonical `STATE_MACHINES.Evidence` before any ledger touch, every transition is audit-before-effect (ledger append precedes the in-memory status flip, and a throwing ledger leaves the record on its prior status), and both real consumers (`knowledge-claim-service`, `temporal-ledgers`) call `resolveAccepted`/`toEvidenceLookup` live at cite-time rather than caching a resolution — so there is no ordinary check-then-act window inside the ladder itself, and the module's own 36 tests plus the full 1146-test suite all pass unmodified.

However, adversarial testing surfaced **one genuine, previously-undetected, and easily-reproducible integrity gap that neither the dedicated S1 review nor the one holistic completion review probed**: `EvidenceEnvelopeService`'s entire register/seal/verify/accept lifecycle state lives *exclusively* in an in-process `#records = new Map()`, with **zero rehydration from the durable ledger on construction**. A second `EvidenceEnvelopeService` instance pointed at the *same* ledger file — the ordinary, expected consequence of a process restart, redeploy, crash recovery, or a second worker sharing the ledger — starts with a completely empty `#records` Map. Its `registerEnvelope()` duplicate guard (`DENY_DUPLICATE`) checks only that empty Map, so it **silently accepts a fresh registration for an evidence_id+version that was already SEALED/VERIFIED/ACCEPTED in the ledger**, resetting the service's live view of that identity back to `CAPTURED` with attacker-controlled content. `verifyChain()` and `resolveAccepted()` then both report the identity as if it had never progressed past `CAPTURED` — `verifyChain` returns `valid: true` with empty `sealedVersions`/`acceptedVersions` arrays — even though the ledger file still physically contains the original SEAL/VERIFICATION_REQUEST/VERIFICATION/ACCEPTANCE entries for that exact identity, now silently orphaned and never cross-checked. This directly contradicts the service's own header comment (line 22): *"the ledger hash chain — not the in-memory status field — is the tamper evidence."* That claim is only true while the original in-process `#records` entry survives; it is false across a restart.

This is not a narrow, hard-to-trigger race (unlike, e.g., the MOD-WSPACE-S3 single-writer TOCTOU, which needs a specific concurrent-caller pattern that the module doesn't yet have a live caller for). It is the **deterministic, guaranteed** consequence of the most ordinary operational event — a process restart — for any service that is not, in fact, restart-free for its entire operational lifetime. Nothing in the S1, S2, or S3 review record, nor the holistic completion review, discloses this as a known limitation; the code's own comments claim the opposite. I classify it REQUEST_CHANGES (fast-follow), not a merge-blocker for the already-merged trunk, since the ladder's SoD/edge/audit-before-effect guarantees are otherwise sound and the gap requires a specific (if entirely ordinary) deployment shape to manifest.

## 2. Verify/accept ladder (S2) — SoD, edge legality, audit-before-effect: sound

- **SoD, same-actor gap: NOT FOUND.** `recordVerification` denies `verifier === producer` via `checkProhibitedActors("EVIDENCE_VERIFIER", verifier, { producer }, { ladder: EVIDENCE_VERIFIER_LADDER })` (evidence-envelope-service.mjs:400-406). `acceptEvidence` denies `acceptor ∈ {producer, verifier}` via the kernel's frozen `AUTHORIZE_TIME_LADDER.EVIDENCE_ACCEPTOR` (:456-463). Both are exercised and pass in the shipped suite ("S2 SoD: the producer cannot verify its own evidence", "...cannot accept its own evidence", "...verifier cannot accept the evidence it verified") and I did not find a bypass path (e.g. no alias/case-folding gap in `checkProhibitedActors`, no way to omit `producer`/`evidenceVerifier` from the `history` object supplied at the two call sites).
- **Check-then-act TOCTOU on the ladder edges themselves: NOT FOUND (within one process).** Node's `node --test` execution model here is single-threaded and every ladder method is fully synchronous end-to-end (no `await` between the `record.status` read and the `record.status = target` write); nothing can interleave between them inside one process. The shared `DurableLedger.append()` additionally re-reads and re-verifies the chain **inside its own lock**, comparing the caller's `expectedSequence` against the just-verified record count before writing — so even a stale `expectedSequence` computed by a racing caller against the *ledger* is caught at write time (`DENY_SEQUENCE_CONFLICT`), not silently applied. This is a genuine compare-and-swap at the ledger layer.
- **Identity-continuity gap (MOD-WORK-style, "does a re-version change who verified it"): NOT FOUND at the ladder-mechanics level.** Each `(evidence_id, version)` pair is an independent record (`recordKey`); registering a new version does not inherit any prior version's `verifierActorId`/`acceptorActorId`/status — confirmed by reading `registerEnvelope` (fresh record, `sealedAt: null`, no ladder fields) and by the shipped "duplicate evidence_id+version is denied; a new version registers" test. The **cross-process** identity-continuity break described in §4 below is a different, more serious variant of this same bug class: not a version-bump inheriting the wrong identity, but a *restart* silently erasing which identity the ladder actually ran under.

## 3. Accepted-evidence resolver (S3) — shape validation and stale-read handling: sound

- **Silent-shape-coercion ("grant-shape" class, per MOD-GOV-S3): NOT FOUND.** `resolveAccepted(ref)` treats a non-string/blank `ref` as `DENY_UNKNOWN_EVIDENCE` (`isBlank` gate), never coerces malformed input to a permissive default. Every deny path returns a structured `{ ok: false, code, reason }` — `resolveAccepted` never throws to its callers by design (confirmed: wrapped in the ladder's own `verifyChain` try/catch, converted to `DENY_CHAIN_BROKEN`). `toEvidenceLookup()` correctly reduces any `ok !== true` to `undefined` for the `temporal-ledgers` port shape, never leaking a partial/`ok:false` object as if it were an envelope.
- **REJECTED/SUPERSEDED never resolved as accepted via a stale read: NOT FOUND as a defect, but a completeness note.** `resolveAccepted` requires the *live* `record.status === ACCEPTED_STATE` at call time (re-read from `#records`, not cached) and additionally re-runs `verifyChain(ref)` before returning success — so a version that has since moved past ACCEPTED (in this service's model, only to `SUPERSEDED`/`QUARANTINED`, since the ladder never actually reaches `ACCEPTED → *`) would not be resolvable as stale-accepted. **Completeness note (not a bug):** `STATE_MACHINES.Evidence` defines `REJECTED` and `SUPERSEDED` as legal edges from `VERIFICATION_PENDING`/`VERIFIED`/`ACCEPTED`, but `EvidenceEnvelopeService` implements no method that ever produces those two statuses — `VERDICT_TARGETS` only maps to `VERIFIED`/`QUARANTINED`, and there is no supersession/rejection transition method at all. Since both are terminal states with no outgoing edges in the machine, this is an inert unused-edge gap, not a live bypass; flagging for the record since neither prior review named it.
- **Both real consumers re-verify live, not from a cache:** `knowledge-claim-service.mjs:174` calls `evidenceResolver.resolveAccepted(ref)` directly inside its own proposal path (no caching layer between the port and the call site); `temporal-ledgers.mjs:121` calls `this.#evidenceLookup(ref)` (the `toEvidenceLookup()` closure, which itself re-delegates to a fresh `resolveAccepted` call) at append time. Neither consumer holds a resolution across two separate authorization decisions.

## 4. Seal/ladder-state durability — the one genuine finding (MEDIUM, cross-process/restart)

**Claim under test:** the service's own header comment says the durable ledger — not the in-memory status field — is the tamper evidence, and that `verifyChain()` "requires every sealed record to be backed by a chain-valid seal entry." I tested this literally: does the service's authoritative state survive, and does `verifyChain` actually consult the ledger *independently* of whatever the in-memory `#records` Map currently believes?

**Reproduction** (`repro-rehydrate.mjs`, standalone in the worktree, not committed):

1. "Process A": one `EvidenceEnvelopeService` instance over a real `DurableLedger` file. Register → seal → requestVerification → recordVerification(pass) → acceptEvidence with distinct actors (`producer-A`/`requester-A`/`verifier-B`/`acceptor-C`). Confirmed: `getEnvelope` reports `ACCEPTED`; `resolveAccepted` returns `{ ok: true, envelope: { verification_status: "ACCEPTED" } }`.
2. "Process B": a **brand-new** `EvidenceEnvelopeService` instance constructed against the **same ledger file path** (simulating a restart, redeploy, crash recovery, or a second worker) — nothing else changed; the ledger file on disk is untouched and still contains all four entries from step 1.
   - `serviceB.getEnvelope(...)` → throws `DENY_UNKNOWN_EVIDENCE` (the fresh Map has no record at all).
   - `serviceB.resolveAccepted("ev_repro_001")` → `{ ok: false, code: "DENY_UNKNOWN_EVIDENCE" }` — the previously-ACCEPTED identity is now invisible to this instance, despite the ledger holding its full accepted history.
   - `serviceB.registerEnvelope(env1_forged)` — **same** `evidence_id`/`version`, but different `actor_id` (`producer-EVIL`) and `result` — **succeeds**, no `DENY_DUPLICATE`. The service now reports this identity as freshly `CAPTURED`, with the forged content as its stored envelope.
3. Extended probe: does the ladder let this reset identity run all the way back to `ACCEPTED` under new actors? **No** — `sealEnvelope` on serviceB is denied `DENY_LEDGER_APPEND: Idempotency key was reused for different ledger content`. `DurableLedger.append`'s idempotency-key check is keyed on `["evidence-seal", evidenceId, version]` (content-independent), so it collides with process A's original seal entry and — because the forged envelope's content differs — denies rather than replaying. This is a real, working safety net: it stops the *forged* run from progressing past registration in this exact scenario. `requestVerification`/`recordVerification`/`acceptEvidence` on the reset record then correctly deny `DENY_UNDEFINED_TRANSITION` since the local status is stuck at `CAPTURED`.
4. **But the registration-level reset itself already succeeded**, and it is not benign: `serviceB.verifyChain("ev_repro_001")` after the reset returns `{ valid: true, sealedVersions: [], acceptedVersions: [], quarantinedVersions: [], ledger: { count: 4, ... } }` — **`valid: true`**, reporting this evidence as never-sealed/never-accepted, while the ledger it just read (`count: 4`) physically contains the original SEAL/VERIFICATION_REQUEST/VERIFICATION/ACCEPTANCE entries for the exact same `evidence_id`. `verifyChain` never scans the ledger for entries under an `evidence_id` that isn't currently present in `#records` — it only walks forward from whatever the live Map holds — so a governed, previously-ACCEPTED identity's disappearance from view is reported as a clean, valid chain rather than flagged as an anomaly.

**Why this matters:** the "ledger is the tamper evidence, not the in-memory field" claim (service header, line 22) is only true for as long as the original in-process record survives. Any process boundary — a crash, a redeploy, a second instance, a rolling restart — silently defeats the duplicate-registration guard, hides the fact that a governed acceptance ever happened from every read-path (`getEnvelope`, `resolveAccepted`, `verifyChain`), and lets a new registration under the same `evidence_id`+`version` with **arbitrary different content and a different producer identity** overwrite what the service will report for that identity going forward (bounded, per §4.3, from reaching `ACCEPTED` again only by the ledger's *content-independent* idempotency key — an incidental protection, not a designed one, and one that denies with a generic `DENY_LEDGER_APPEND`/`Idempotency key was reused` message rather than a clear "this identity was already governed" signal). This is squarely the class of bug this project's second-look reviews keep finding: a durability/authority claim in a comment that the code does not actually implement.

**Scope honesty:** I did not find a way to get the forged re-run all the way to `ACCEPTED` — the content-independent idempotency key on the ledger blocks that specific escalation in this exact single-ledger-file scenario. The confirmed, in-scope defect is: (a) the duplicate-registration guard is entirely defeated across a restart/new-instance boundary, (b) a previously-governed identity's status becomes invisible to every read-path after such a boundary, and (c) `verifyChain`'s own "valid" verdict does not detect or flag this loss, contradicting its documented purpose.

## 7. Recommendation (non-blocking, for a fast-follow)

1. On `EvidenceEnvelopeService` construction, rehydrate `#records` from the durable ledger's existing entries (SEAL/VERIFICATION_REQUEST/VERIFICATION/ACCEPTANCE payloads carry the full envelope and status transitions needed to reconstruct state) **or** have `registerEnvelope` consult the ledger directly for any prior entry bearing the candidate's `evidence_id`+`version` before admitting a registration, not just the in-memory Map.
2. Have `verifyChain` scan the ledger for `evidence_id`-matching entries that are **not** represented in the current `#records` snapshot and deny (`DENY_CHAIN_BROKEN` or a new dedicated code) rather than reporting `valid: true` — closing the gap between the documented tamper-evidence claim and the actual check.
3. Until (1)/(2) land, document explicitly (in the service header and any deployment/ops guidance) that `EvidenceEnvelopeService` requires exactly one continuously-running instance per ledger file for the lifetime of any evidence it governs — today that constraint is assumed, not enforced or even stated.
